# Pagination

A list that grows without limit is read one page at a time, and every page in the product has the same shape: the items, and an opaque cursor that says where the next page starts. The cursor is the last row's sort key rather than a count of rows skipped, because the event log is only ever appended to, and a count would repeat or skip rows whenever a new event lands between two pages. The same shape is cut from two kinds of source, a Postgres query inside withFamily and a sorted list already in memory, so a screen that pages through lessons today can page through a server route tomorrow without changing.

This document covers that shape and where it is built, how search works over paged lists, the client primitive that screens use, the first two uses (the picture wall on the server and Explore's shelves in the browser) with the measurements taken before and after Explore changed, and the lists we expect to page next. It also records one problem that looks like pagination and is not: the record replaying a child's whole event log.

## The shape

`Page<T>` in `engine/page.ts` is `{ items, next, total? }`. `items` is the page, in the list's order. `next` is null on the last page and otherwise a cursor, a short string that only `readCursor` in the same file reads. `total` is how many items match the query, where the source can count them cheaply; the picture wall sends it on the first page only, and a list in memory sends it on every page because counting costs nothing there.

A cursor is base64url text holding a small JSON array: a hash of the query the page was cut under, then the last item's sort key, most significant part first. Nothing outside `engine/page.ts` builds or reads that text, so the format can change without touching a screen or a route. `readCursor(raw, query, shape)` takes the raw value as `unknown`, since it arrives from outside the program, and returns either the key or a problem. It refuses a value that is not a string, is longer than 512 characters, does not decode, is not JSON, does not match the list's key shape (the number of parts, and each part a string, a number or a string matching a pattern such as a uuid), or was made under a different query. A route answers any of these with `400 bad-request`, the same as any other malformed parameter.

`limitOf(raw, max, fallback)` reads a page size from a request. It clamps a whole number to between 1 and `max`, and uses `fallback` when the request names none or names something that is not a number. The picture wall allows 48 and defaults to 24.

The sort key must be unique across the list, which in practice means it ends with the row's id, and it must compare the same way everywhere it is used. `compareKeys` compares strings by code unit, which is how Postgres compares text under the "C" collation and how it compares uuids and our canonical timestamps under any collation. A key we page by in SQL is therefore made of timestamps, numbers and ids, never of text a person wrote, and a list in memory is sorted with `compareKeys` itself. Explore's order used `localeCompare` for the lesson's file name before this change; switching it to `compareKeys` changed the order of none of the 504 lessons in the current pack, and a test would catch a file name for which it did.

## Keyset rather than offset

An offset says "skip forty rows and give me twenty". It is simple, and it is wrong for any list that changes while it is being read. If a row is added above the reader's place between two pages, every row shifts down by one and the next page repeats the last row of the previous one; if a row is removed, the next page skips one. On the event log, rows are added all the time, and on the picture wall a picture painted again moves to the top. An offset also makes the database read and discard every skipped row, so the fortieth page costs forty times the first.

A keyset says "give me twenty rows that come after this key". Rows added or removed above the reader's place do not move it, because the place is a value rather than a position. A row that moves from below the cursor to above it (a picture painted again while a parent scrolls the wall) is not shown twice and does not push anything else out; it is simply not on the rest of this reading, and it is at the top the next time the list is opened. With an index on the key, every page costs the same.

What a keyset cannot do is jump to page 7, and it cannot say which page a row is on. Nothing in the product needs either. A screen shows the first page, then more as the reader goes, and a search replaces jumping.

## The two sources

`pageOfList(sorted, keyOf, at)` in `engine/page.ts` cuts a page from a list that is already narrowed and sorted and does not change while it is read, such as the lessons in a pack's index. It finds the first item whose key is past the cursor by binary search, so a cursor whose own item has since gone still lands in the right place, and it returns the same `Page<T>` a route would.

`pageOf(tx, order, at, read, count?)` in `server/db/page.ts` cuts a page from a Drizzle query. `order` names the key columns and one direction for all of them, and how to read the key back from a row. `pageOf` builds the row comparison `(k1, k2) > (v1, v2)` (or `<` for a descending list), the `ORDER BY` on the same columns and a limit of one more than the page, and hands those to `read`, which adds them to the list's own query. The extra row tells it whether there is a next page without a second query. It takes a `FamilyTx`, the transaction type that only `withFamily` makes, so it cannot be called on an owner connection that would bypass row-level security, and the rows it pages have already been narrowed to the family by the policies before any page is cut. A cursor carries a place in the order and nothing else, so a cursor taken from another family's list and replayed here moves the reader to that place in this family's rows and shows nothing of the other family; `server/db/__tests__/page.itest.ts` holds that.

The two sources share the key comparison and the cursor format, so the same screen code reads either, and a list that moves from memory to a route keeps its cursors' meaning.

## Search over paged lists

A search is part of the page request, not a filter over what a screen already has. Every source applies the query and the filters to the whole list first and only then cuts the page, so the second page of a search is the second page of its matches, and a match on a page never loaded is still found. A screen never searches only the pages it has read.

A cursor is bound to its query. The hash at its front is taken over the list's name and everything that narrows it (for Explore, the shelf and the filters with the words as the search reads them; for the wall, the gallery and the search words), and `readCursor` refuses a cursor made under anything else. So a "next" left over from an older search can never be used to read the second page of a newer one, which would otherwise mix two sets of results. The hash is not a secret and does not need to be: forging one only lets a caller move within rows they may already read.

Results keep a stable, documented order, the list's own. Explore keeps the catalogue's order (grade, then subject in the tracks' order, then the order a subject is taken in: unit, then file) and groups results by shelf, so a search does not reshuffle the page. Neither list ranks by relevance today. If one does, the rank becomes the first part of the key, with the id after it, so two results with the same rank are still ordered and never repeat or skip across a page boundary.

On the server, `pageOf` takes the match as an SQL predicate and adds it to the list's query before the keyset comparison. The picture wall's titles are searched with Postgres full-text search in the `simple` configuration, through a GIN index on `to_tsvector('simple', title)` (`artworks_title_idx`, added by `0010_picture_wall_pages.sql`). Each word the parent types becomes a prefix term, and all of them must match, so "blu wha" finds "Blue whale". We chose full-text search over trigram matching because it needs no extension: [migrations.md](migrations.md) keeps the schema to plain Postgres so the same history runs on the local container and on Neon, and `pg_trgm` would be the first extension. The `simple` configuration does no stemming and drops no stop words, which suits short titles written by children in any language. The cost is that a word matches only from its start, so "hale" does not find "whale", where Explore's search, which runs in memory, matches a fragment anywhere in a word. We have not seen a parent search the wall by the middle of a word, and trigram remains the option if that changes. The route keeps only letters and digits from what was typed, at most eight words and at most 100 characters, so nothing typed can become an operator in the text-search query. The search runs inside `withFamily` like every other read.

## The client primitive

`engine/ui/paged.ts` holds the logic of a paged list on a screen, with no Solid in it, so Node's test runner covers it (`engine/ui/__tests__/paged.test.ts`). A `Source<T, F>` is a function from the filters, a cursor and a page size to a promise of a page or a failure; a list in memory and a route are both one. `pager` asks for one page at a time and ignores a second ask while the first is on its way. It numbers every ask, and an answer to any ask but the latest is dropped, so a slow answer to an older search never lands over the answer to a newer one. `restart(filters)` starts the list again from the top under new filters. It keeps the items already shown until the first page of the new search arrives and then replaces them, so a list does not blink empty on every keystroke; if that first page fails, the old items are cleared rather than left to read as the new search's results. A failure stops the list until `again()` is called.

`engine/ui/paged-list.tsx` is its Solid face. `createPaged(source, filters, { limit, lazy })` makes the pager, keeps its state in a signal, and restarts it whenever the `filters` accessor changes. With `lazy`, a list asks for nothing until its end first comes near, so a list far down a screen costs nothing until the reader scrolls toward it.

A paged list scrolls on with nothing to press: there is no button that reads more, no page numbers and no next or previous. `ListEnd` is the end of a list. It asks for the next page while the end is still a whole window below the view, so a reader scrolling at an ordinary pace never reaches the bottom before the next page is there; that window is the page read ahead, and for Explore's shelves, which read from memory, it is about one page on a phone. An intersection observer says only when the end starts or stops being near, not that it is still near after a page arrives, so `ListEnd` observes the end again after each page it reads while the end was near, which makes the observer report once more; a tall window keeps reading until the end is out of reach or the list is done.

A keyboard and a screen reader read on without a button. `readOnLastFocus` goes on the list's element: when focus arrives on the last item read, by Tab or by an arrow, it asks for the next page, and the item keeps the focus because the page is added after it. When a page after the first arrives, a polite live region at the list's end says how many came ("6 more lessons in Grade 1 Maths"), which is visible only to a screen reader. While a page is on its way, the same place shows a quiet line, "Loading more", which is text and not a control. At the true end of a list nothing is said; Explore's shelves each say how many they hold in their heading, so an end note under every shelf would only repeat it. A failed page shows one line, the failure in a parent's words and a Try again link, which does not cover the list or stop it scrolling, and the list also tries again by itself the next time the page is scrolled.

A heading may still say how many a list holds ("15 lessons", or "7 of 15 match" while words are searched). That is a count and not a way to move through the list.

A screen with a search box debounces typing by 250 ms, keeps the words in the address as `q`, restarts every list on the screen when the words change, and says what was searched when nothing was found, with a button for each filter that could be widened.

## Explore, step 1

Explore used to lay out all 504 lessons at once and hide the ones a search did not match, so the first paint built every tile. It now pages each shelf, a grade's lessons in one subject, over the index it already has in memory. The pack index is still fetched whole, as before, since it is 60 KB gzipped and every view needs it; what changed is that Explore no longer builds the whole catalogue from it at once.

Each shelf is a lazy paged list of six tiles a page, two rows at a desk and three on a phone. A shelf shows its heading with its count ("15 lessons") until it comes near, then its first page, and more as the parent scrolls or tabs through its tiles. The grade headings and their counts are there from the start, so the page is as long as it was and a parent can still fold a grade away.

The search box sits above every shelf and is shared by all of them; each shelf pages its own matches. The counts (the total in the search line, each grade's, and each shelf's "7 of 15 match") are worked out from `found` over the whole index, not from what has been read, so a search looks at every grade, a folded one included, and opens a folded grade that holds a match as it did before. A shelf with no match is hidden, and a grade with none is hidden with it. The total is read out through the search line's `aria-live` region ("112 lessons found"). When nothing matches, a card says what was searched ("No lesson matches “volcano” in Grade 2 · Writing.") with a button to clear each filter that is set.

The filters, `found` and the page of one shelf (`shelfPage`) moved from `apps/home/catalogue.ts` to `school/catalogue.ts`, which the server may import, so a later route that cuts Explore's pages on the server applies the same filter and the same order. The address still holds the grade, the subject and the words. A lesson's own address still opens its preview when that lesson's shelf has not read that far, since the preview finds the lesson in the index rather than among the tiles. Printing is unchanged and does not depend on scrolling: Explore's catalogue is never printed as a whole, since a print from Explore is one lesson's sheet alone, laid out off the screen from that lesson's own file, and the print stylesheet hides the catalogue. So nothing reads the rest of the shelves before `beforeprint`. A list that is printed whole one day will need to read its remaining pages first. Solid's list keeps a tile whose lesson is still on the page when a search changes, so a picture already drawn is not drawn again.

### The measurements

We measured Explore the way [map-stability-stages.md](map-stability-stages.md) measures the map: Chrome with the iPhone profile (430 by 932 at a device pixel ratio of 3, mobile and touch), against the dev server on 8500, signed in as a new family with three children, each run a fresh load of `/explore`. Three runs at full CPU speed and three at a quarter (Chrome's CPU throttling set to 4) were taken before the change and after it. Time to the first tile is from navigation start to the first `.explore-tile` in the document. DOM nodes are counted at that moment and again three seconds later, when the pictures near the view have drawn. Memory is Chrome's used JavaScript heap after a forced garbage collection at the three-second mark. The script ran as a Playwright case outside the repository; it is short, and this paragraph is enough to write it again.

| Explore on the iPhone profile | Before | After |
|---|---|---|
| Tiles built on the first paint | 504 | 6 (120 three seconds later) |
| DOM nodes at the first tile | about 3,030 | about 760 |
| DOM nodes three seconds later | 6,066 | 5,813 |
| Time to the first tile, full CPU | 166 to 190 ms | 190 to 202 ms |
| Time to the first tile, CPU at a quarter | 414 to 451 ms | 331 to 579 ms |
| JavaScript heap after garbage collection | 23 MB | 24.4 MB |

The "after" column was measured on 29 September 2026 against the paged catalogue, with 552 lessons in the index where the "before" column had 504, by `.scratchpad/grades56/closing/explore-measure/` (a Playwright case and its config). The first paint now builds one page of the first shelf, and the page reaches its first tile with a quarter of the nodes. Three seconds later the shelves near the view have read on to 120 tiles, and about 4,600 of the 5,813 nodes are the tiles' drawings, so the settled page is close to the old one in size; the saving is in the first paint and in the shelves far down, which read nothing until they are scrolled to. Time to the first tile did not improve, which suggests it is bound by the pack index and the drawings' code rather than by the number of tiles. We have not measured this on a phone.

These are measurements of a desktop browser under a phone's profile, not of a phone. The dev server serves modules unbundled, which affects both columns equally. The heap is the whole page's, including the pack index, the router and the grown-ups' bar, which is why it moves less than the node count.

## The picture wall on the page

The picture wall (`engine/ui/painting-gallery.tsx`) read its route with a loop of its own: a first page in a resource, a "More pictures" button, and a scroll handler and an observer that both pressed it. It now reads through `createPaged` like Explore's shelves. Its source is the painting gateway's `list`, its filters are whose pictures are shown and a count that goes up whenever a picture is saved, copied or deleted, so the wall reads again from the top without blinking empty, and the drafts kept on the device are a resource of their own beside it. The pictures are a list, so `readOnLastFocus` reads on when focus reaches the last one, and `ListEnd` sits under them with nothing to press. The wall scrolls inside its dialog rather than on the page, so `ListEnd` takes a `root`, the box the list scrolls in, which its observer measures the end against and whose scroll retries a failed page. A failure to read the wall is `ListEnd`'s one line with Try again, as on every other paged list.

## Planned, not built: the server route for the pack index

This route is planned for later and does not exist yet. The pack index is read whole by every view today, and at 504 lessons it is 60 KB gzipped, which is the budget [api.md](api.md) sets for it. Explore's shelves page over it in memory, which costs nothing on the network. The route to build later is `GET /api/pack/<digest>/lessons?grade=&subject=&q=&after=&limit=`, which answers a `Page<LessonFacts>` from the same `shelfPage` over the server's copy of the index. We would build it when the index outgrows its budget, which at today's size per lesson is somewhere past a thousand lessons, or when a family's own authored lessons join the catalogue and make the index per family rather than per pack. Until then a route would add a round trip to every shelf for no saving. When it comes, Explore changes its source from a function over the index to a function over the route, and nothing else, since both return the same page and bind their cursors the same way; the deep link would then read the one lesson it names from the index route that already serves a lesson's file.

## What to page next

The event log view. `GET /api/events` answers a family's whole log, narrowed by kind and by day, and the calendar reads a year of it that way. A view that shows the log itself (a parent reading what happened, or a support view) should page it by `(at, id)` newest first, with the kinds and days as filters bound into the cursor. This is the case the keyset exists for: the log is appended to while it is read.

Tutoring turns. A long teaching session's turns are read whole when it is opened. They are appended in order and never change, so they page by `(seq)` within the session, oldest first, with the newest page read first when a parent reopens a session.

Mail deliveries. The weekly letters' delivery rows grow by one per recipient per week. An operator's view of them, or a parent's list of letters sent, pages by `(week, id)` newest first, with the status as a filter.

Each of these is a `pageOf` over its own query, an index on its key through a migration, and a route that reads its cursor and page size as the picture wall's does.

## Planned, not built: the record's snapshot

The snapshot described here is planned for later and does not exist yet. The record a child's view and a grown-up's page read is a fold of that child's whole event log, worked out on every read (`childRecord` in `school/family/family.ts`). That cost grows with the log, a term of work being megabytes, and it can look like something pagination would fix. It is not: the fold needs every event to be right, because progress, rewards and plans are worked out from events and never stored, so reading the log a page at a time would only spread the same work over more requests. What would fix it is a snapshot: the fold as it stood at some event, kept with the id of that event, so a read folds only the events after it. That is a separate design, with its own questions (where a snapshot is kept without breaking the rule that nothing derived is stored as truth, when it is thrown away, and how a change to the fold's code invalidates it), and it belongs in [db.md](db.md) and [data-model.md](data-model.md) when it is taken up.
