## 3. How the work is done

### The rules

Read `CLAUDE.md` at the repository root first. The levels notation is described in `.docs/notation.md`, section Levels, and the way an author writes a level is in `.docs/authoring.md`, section Easier and harder. The brief every levels batch followed is `lesson-levels/batch-brief.md`, and the plan with its reasons is `lesson-levels/plan.md` (both under the working folder in section 7).

There are no commits in this repository. Before a file is rewritten it is copied into a `backup-<name>/` folder beside the work, keeping its path from the repository root. No lesson or item is ever deleted or renamed.

Heavy checks follow `work/CHECKS.md` in full: the suite, `npm run check`, the print check, playwright, the corpus verifier over the whole corpus, `npm run pack` and a production build each take the shared lock `work/check.lock` (a directory, with a `who` file naming the holder and the time), run under a time limit (20 minutes for a suite, the root check or the print check, 10 for a build or the pack), and release the lock in a trap on EXIT. Nobody starts a heavy check while the load average is over about 20. A single `npx tsc --noEmit` is light.

The levels stream has its own lock as well, `lesson-levels/check.lock`, taken by `lesson-levels/scripts/with-lock.mjs` (which writes an `owner` file, not `who`). The catalog lead's landings run under it. The order is always the levels lock first, the shared lock inside it, and the browser lock (`work/browser.lock`) innermost, because the other order deadlocked wave 10's print check.

### How a level is written

Medium is written first and finished: goal, sections, seeds and the grown-ups note. Easy and hard then go into the same file without changing anything medium asks.

- In an item, a `level easy { ... }` or `level hard { ... }` container may hold `let`, `set`, `where`, `hint` and `scene`. A `let` narrows a parameter the item already declares to one end of its range. A level may never add a parameter, since that renames every version medium asks.
- Every item that gains bands gets a `difficulty` line, an expression in its parameters that is larger for a harder version (`difficulty (10 - n)`, or a hand ranking with `if` and the reason as a comment). An item whose versions have no honest order gets no line and counts for nothing.
- In a lesson, a setting prefixed with a level changes a block at that level only: `easy-count=2`, `hard-a=9`, `hard-seed=7`, `count=0` at a level removes the block. `level=medium` on a block makes it use the item as written, which is how easy works one of medium's own versions in the teacher's pen, and how a `show` pinned outside a level's band is kept.
- Every level keeps a two-star and a three-star question, pinned smaller at easy and larger at hard, and hard carries a second reasoning question in its core.
- Each level has one grown-ups sentence, `level easy { grown-ups "..." }`, that says what that level changes. The shared note does not change. Child copy has no exclamation marks and no em-dashes.
- Expressions are written exactly as the formatter prints them, since the suite's syntax test fails on any other spelling.

### How a level is checked

The verifier resolves each level on the syntax tree and checks it as a plain lesson: every version proved, no feedback true for a right answer, pins inside the level's range, no practice count above the level's number of versions, no version asked twice at one level. The lesson measure is the mean over a level's questions of each version's difficulty, taken against the item's versions as written (medium's mean subtracted, divided by the spread, at least 1). It must rise from easy to medium to hard. A fall is an error; a rise of 0.05 or less is a warning; and `test/content.test.ts` holds the exact list of warnings (two known ones, apples-to-ten and make-ten), so a flat level fails the suite. The review page marks two levels less than 0.15 apart.

The scripts a batch uses, all in `lesson-levels/scripts/`, run from any directory with `node --import /Users/naib/Documents/code/lumischool/tools/scripts/resolve.ts --disable-warning=ExperimentalWarning <script>`:

- `issues.ts`: the corpus's errors and warnings; it must print 0 errors and exactly the two known warnings.
- `levels-report.ts`: every levelled lesson's measure per level (`ITEMS=prefix` limits it).
- `answers-at.ts` with `ITEMS=id,id`: the answers each level of an item gives. A level whose every version has the same answer is a finding.
- `seed-scan.ts` and `seed-answers.ts` with `ITEM=`, `LEVEL=`, `COUNT=`: what each seed draws, to choose an `easy-seed=` or `hard-seed=`.
- `dump-lesson.ts <ids>`: every question at every level as the child meets it.
- `b24-seeds.ts` with `OVERLAY=<staged src folder> ITEMS=id,id COUNT=n`: the same seed scan over a staged batch that is not on the tree yet, printing each draw's short parameters and answer. It is read-only.
- `baseline-diff.py <before.json> [after.json]`: which lessons and items a baseline regeneration added, removed or changed; it exits non-zero if anything was removed or changed.

The catalog lead's staged batches are checked with `catalog-balance/scripts/pilot-check.ts` (`OVERLAY=<folder>` checks a batch's staged files over the tree read-only, `FAST=1` limits the workspace, `DUMP=1` prints every question at every level into the batch's `dump.txt`, and `report.json` gets the measures). Landings go through `catalog-balance/scripts/land-queue.sh`, which takes the levels lock, then the shared lock, runs the precheck, copies the new files with backups, regenerates the baseline, and runs `land-checks.sh`: tsc, the suite (20 minutes), the print check on its own server (`with-print-server.sh`, 20 minutes), the sheet counts, and `npm run pack` at the root (10 minutes) with the index size.

The print rule: each level prints as its own lesson, exactly the sheets it lays out, and no level prints more than one child's sheet over medium. The pack rule: the index stays under 60000 bytes gzipped and a lesson file under 50000.

### The baseline and when it may be regenerated

`.scratchpad/test/levels-baseline.json` records every question each lesson asks as written and every item's versions, and `test/levels.test.ts` fails if the tree differs from it. It is written by `.scratchpad/scripts/levels-baseline.ts` (the catalog lead's landing runs it directly; the brief calls it `npm run levels:baseline`, which is not in the scratchpad's package.json). It may be regenerated only in two cases: a new lesson or item, which has no earlier medium to keep; or a deliberate change to a lesson as written, such as a wrong key, with the reason written in that batch's notes. Adding or editing a level never needs it, and a medium seed on a lesson already in the baseline is never moved to make a level, since that changes what every child at medium has been asked. A new lesson's medium seed can still be chosen before its first landing.

Before each landing that regenerates the baseline, copy the file (`cp .scratchpad/test/levels-baseline.json lesson-levels/baseline-before-<batch>.json`), and after the landing run `baseline-diff.py` against the copy. The result must be exactly the new lessons and items added, with nothing removed or changed.

### The reader's checklist

The second reader reads the batch's `dump.txt` at every level, and the lesson and item sources, for what the verifier cannot see. What this stream's readings actually found, in the order worth checking:

1. Every right answer worked by hand, and every distractor checked to be wrong at every version (for music and coding this meant reading the chord book in `engine/sound/fretted.ts`, the part drawings in `engine/parts/`, and the interpreter's defaults in `engine/coding.ts`).
2. A picture that disagrees with its text or gives the answer away: a template drawn with a fixed number of lines under a question that asks for the number, a tab that prints the string letter when the question names an open string, a hand drawn on the wrong side, a hint that says notes are joined when the part draws them flagged.
3. An earlier question, or the look, that answers a later one: a lesson that numbers a snack's steps before asking which two lines of the same snack are swapped; two hard reasoning questions with the same right answer two questions apart; a count asked in question 1 and then the bar with that count asked in question 3.
4. A level whose questions are medium's own, where the band allows otherwise: move the level's seed, or have the worked example use medium's own version and practise the others.
5. A run of the same answer key (four "Lamp 2" answers in a row), and a band whose every version gives the same answer at a level.
6. A hard draw that sits below medium's own draw on the item's difficulty line, usually because medium's seed takes the item's hardest version: widen the range so hard has something above it.
7. The grown-ups line for each level, clause by clause against that level's draws: a clause that names no change, a wrong message or count, or a description that fits the band but not the version drawn.
8. Child copy: plurals set by a number ("1 up strums"), a template sentence that breaks grammar ("where does the chord first changes"), wording that allows two readings of the rule ("with crotchets and minims"), and em-dashes or exclamation marks.
9. For every seed change proposed, the draw found with a seed scan and its effect on the measure worked out, so the finding says whether the measure moves.

Findings go back as must-fixes (wrong answers, pictures or copy that mislead, a reasoning question answered by the page) and should-fixes (overlaps, flat or repeated draws, lines to reword), plus the entries for the owner's list. The fixed dump is read again before the batch is cleared. The catalog lead records the findings in its `batchNN-notes.md`, so a batch whose notes have a reader's section has been read.
