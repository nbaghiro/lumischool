# The database module

Weekly email adds `mail_preferences` and `mail_deliveries` through `0001_weekly_mail.sql`, bringing
the database to nine tables. Both force family RLS. The scheduler enumerates only active parent
recipient IDs through a narrow security-definer function, then reads all data through `withFamily`.
Delivery leases and a family/recipient/week unique key survive restarts. Payloads are cleared once
dispatch is terminal; child deletion and consent withdrawal suppress retained family payloads.
The original seven-table discussion below describes product data, not these operational records.

Kids’ sign-in uses the same seven tables. The `kids_username_key` unique expression index covers
`lower(settings->>'username')` across families; missing usernames remain null. A `kid-pin` key per
family is protected by `keys_kid_pin_key`. `kid-attempt` keys can have no family and hold only hashed
username/network identities. The narrow `kid_login_lookup` SECURITY DEFINER function serializes
attempt limits before finding an enabled username; it grants execution only to the app role and
fixes its search path. Subsequent PIN checks and reads run through the selected family’s RLS scope.

The module is `server/db/`. It was `store/` until the owner chose the root layout in September 2026, and was renamed so it is not confused with a store on the client.

Status: built and tested locally to the owner's final data model, and to [auth.md](auth.md) where it asks things of the store, September 2026. This is the local database: Postgres in Docker, the seven tables the model settled on, the row-level security that keeps one family's data out of another's reach, the migration setup and the tests and guard around them. Deployment is not in scope; the owner expects it to follow galleo onto Render and Neon. Sync is our own and small; the owner decided against PowerSync after a trial, as the section on what lives on the device says.

What was decided, and why, is recorded in [data-model.md](data-model.md) under "Decided". This document is how it was built.

## How to run it

Every command runs from the repository root, and none needs a `.env`: with no URL set, the store reaches the local container, as the owner for migrations and as `lumischool_app` for everything else.

| Command | What it does |
|---|---|
| `npm run db:up` | Starts the container, waits until it is ready, and gives the app role its local login. Fails if it is not ready in 30 seconds |
| `npm run db:migrate` | Applies every migration not yet applied. A second run does nothing |
| `npm run db:reset` | Drops everything in the `lumischool` database, then applies migrations without adding application data. Leaves the volume and the test database alone |
| `npm run db:generate` | Writes a new migration from the difference between `server/db/schema.ts` and the last snapshot |
| `npm run db:check` | Checks the migration folder is consistent |
| `npm run db:psql` | Opens `psql` inside the container, as the owner |
| `npm run db:down` | Removes the container and keeps the volume |
| `npm run check` | Type check, the guard, and the integration tests |

The first time on a machine: `npm install`, `npm run db:up`, `npm run db:reset`. The ports and the rest of the local setup are in [local.md](local.md).

## What lives in Postgres and what lives on the device

A child's device keeps no copy of the log. The app is online first: a children's view reads a child's record from the API each time it opens a page, and keeps only the answers it has not sent yet, in a short queue in the browser that empties as each chunk lands ([auth.md](auth.md), flow 8). Postgres holds the family's log, plus what belongs to more than one person or more than one browser: the grown-ups' logins, their memberships, the keys that sessions, children's views, the family's PIN and codes are checked against, and the content a parent wrote. An event is one row of `events` column for column, and a draft in the queue is the same row less what the server stamps, so moving it is a copy.

None of the seven tables exists to make sync work, which was the test for a first schema: with one device and no sync at all, every table would still be needed. We trialled PowerSync, self-hosted, as the engine that would copy `events` to devices, and in September 2026 the owner decided against it: a replicated local database is more than a child's view needs. Our sync is an upload of drafts through `withFamily`, where `id` makes a chunk sent again write nothing twice and the server stamps `device` and `seq` under the family's lock, one stream per key, and a read of what the page has to show. The one change the trial asked of the schema, a single text format for timestamps, stays, because it is what lets the wire and the database hold identical rows.

## Why `server/db/` exists now, and what it becomes

[structure.md](structure.md) recommends no backend module until there is a backend, and one `server/` module holding `http.ts`, `store.ts` and `jobs.ts` when there is. It names this directory as a backend module arriving early, a decision to confirm or reverse.

We agree there is no server, and an empty one is three files that guess. The store is the one of the three that does not have to guess: the data model is decided, the schema follows from it, and the properties that matter most (one family's rows unreachable from another's, a replayed upload written once, a kid deleted in one statement, a new answer kind with no migration) can only be checked against a real Postgres. The owner asked for the local database and the migration setup to be settled before the data is populated, and nothing here is an HTTP layer or a job runner.

Under that recommendation the move is mechanical. The files in `server/db/` become sections of `server/store.ts`, `server/db/migrations/` becomes `server/migrations/`, and `drizzle.config.ts` and the guard change their paths. `engine/answer.ts` is a directory holding one file where the recommended tree has a root file `answer.ts`; that is one rename and a handful of import paths.

## What the siblings do and what we took

Galleo is the closest and the one deployment will follow: Drizzle with postgres-js, a pinned image with a named volume and a healthcheck, checked-in SQL migrations applied in the Render build, and the client kept apart from the schema. We took all of that, built the handle on first use rather than at import, gave the local URL a default rather than an empty string, and added a reset, which galleo lacks. Galleo's integration tests reach the schema with `drizzle-kit push --force` rather than by applying its migrations, so they never run what deploys; ours apply the real files.

Llamatrade (Python, SQLAlchemy and Alembic) keeps tenants apart with row-level security keyed on a transaction-local setting and tests that the list of secured tables has not drifted; its ledger is an append-only log with an idempotency key; its tests skip without Docker unless a variable says the database is required. We took all four ideas. We did not take its projections with checkpoints, because our scale does not need them.

Flowmaestro uses raw SQL with row types kept in step by hand, which is the drift declaring things once is meant to avoid. BullMQ is a dependency nothing imports, and its root `db:reset` calls a script that does not exist, which is why every script in the table above was run while this was built.

Clientbridge runs PowerSync self-hosted on the same shape of Postgres. It was the template for our trial, which the owner decided not to adopt.

## The seven tables

The rule for columns was the owner's: a column the code or the database can derive is not stored. So there is no `created_at` except on `keys`, where it is what an expiry is measured from; no role column on `members`, because a membership with no kid is a parent; and no hash to keep in step on `content`, because Postgres generates it. Foreign key columns are `family_id`, `user_id` and `kid_id` everywhere, which keeps the reserved word `user` out of every query. There is no enum type, no view, and no column derived from an event's data.

| Table | What it is for |
|---|---|
| `families` | The tenant: a name and a time zone. A family's records are days, and a day is only a day in one zone |
| `users` | A grown-up's login: an email address (unique however it is capitalised), a name, the public half of any passkeys, and `settings`, what they chose for themselves (their picture, by the shelf's name for it), as a kid's `settings` holds a child's. No family column and no password |
| `members` | Who belongs to a family. A parent has no kid and no window; a tutor has one kid and a window of days. `ended_at` is set when someone is removed, so their name stays readable in the family's history, and grants nothing |
| `kids` | A name, a grade and the settings a parent chose, and nothing that identifies or reaches a child |
| `keys` | Every secret we keep the hash of: sessions, one child's key in a children's view, the family's PIN, and the codes a person is emailed or shown |
| `events` | The log: one row per event, appended and never updated |
| `content` | Notation a family wrote, and our catalogue, addressed by the hash of the body. A pack is a row too, whose body is its manifest |

### One shape per row, and one format for time

A row has one shape everywhere. The properties of every table in `server/db/schema.ts` are its column names, snake_case (`family_id`, `kid_id`, `seen_at`), so `typeof events.$inferSelect` is the same object Postgres returns and the wire carries, and each row type is exported beside its table under its singular name: `Family`, `User`, `Member`, `Kid`, `Key`, `Event`, `Content`. `Envelope` in `engine/answer.ts` stays the union correlated by kind, with exactly the events row's keys and field types, and `server/db/__tests__/schema.test.ts` fails the type check if the two drift in any key or field.

Every timestamp is text in one format, ISO 8601 in UTC to the millisecond, as `toISOString` writes it (`2026-09-14T09:12:00.000Z`): `events.at`, `members.ended_at`, `keys.created_at` and `keys.seen_at`. A check on each column refuses any other shape, `check` refuses it at the edge, and `utc_iso()` in the migration renders `now()` into it for defaults and windows. We store text rather than `timestamptz` because Postgres renders a timestamptz as `2026-09-09 09:38:00+00` and JavaScript as `2026-09-09T09:38:00.000Z`; converting at each edge would leave a page holding its own drafts in one format and the rows it reads back in another, and since a space sorts before `T`, ordering by `at` in the page would be wrong. Stored as one fixed-width string, the value is identical everywhere and text order is time order. Dates (`from_day`, `to_day`) stay `date`, which reads the same everywhere already.

Every foreign key cascades, and every one that names a kid names the family with it, `(family_id, kid_id)`, so a bug cannot attach a row to another family's kid: the pair does not exist. Deleting a kid is one statement and takes their events, any tutor's membership on them, and the keys of every children's view opened for them, which hold nothing of the child's to erase. Deleting a family is the same cascade one level up. There is no soft delete anywhere, because `.scratchpad/src/family/privacy.ts` refuses one.

### Memberships and the last parent

Two parents in one family is the normal case, and they have equal rights; there is no owner. A person has one parent row per family and one tutor row per kid, enforced by two partial unique indexes, and a check refuses a parent with a window or a tutor without a kid and both days.

A family always has at least one active parent, and two triggers hold that. The first refuses, at the statement that tried, the removal that would leave none: deleting the last parent, ending their membership, turning them into a tutor, or deleting their login (which reaches the membership by cascade). It locks the family row first, so two people removing the last two parents at the same moment are taken in turn and the second is refused. The second trigger is deferred to commit, which is what stops a family being created with no parent at all. Creating a family and its first parent is one call, `create_family`, and the first parent is whoever is signed in.

### Keys

Seven kinds share one table because every one of them is found by a hash, expires by a rule, and those a person is emailed are counted by the rate limits. A children's view opened for several children holds one `kid-session` key per child, so `kid_id` is a scalar with a real foreign key and there is no list of kids anywhere.

Expiry is a rule per kind, declared once in `server/db/keys.ts` as a complete record over the kinds, so a new kind cannot be added without deciding how long it lives: sign-in and confirm codes last ten minutes from when they were made, an invitation seven days, a session and a kid session thirty days from when they were last seen and ninety from when they were made, a shared session thirty minutes idle and twelve hours in all, and a family's PIN until a parent sets it again. A code that has been used is deleted rather than marked, because the event it produced is the record.

There are two ways to a key. A session, a shared session, a kid session and an invitation are named by a credential, `<family>.<id>.<secret>`, which carries its family, so they are read inside `withFamily` for that family and checked under its policy; while one family's credential is being checked, nothing about another family is reachable. A family's `pin` key is read inside the transaction of a children's view in that family, since nobody holds a credential for it, and its hash is a keyed hash of the family's id and the digits under a key that is not in the database. Two kinds belong to no family while they are in use, which the checks on the table allow and nothing else: a sign-in code and a confirm code. The app role cannot reach either through a policy, so they are reached only through security-definer functions, each by the hash of a secret the caller holds:

| Function | What it does |
|---|---|
| `key_issue` | Makes a sign-in or confirm code, held by the browser's pending cookie, if the limits allow |
| `key_prove` | Checks a guess at a sign-in or confirm code found by the pending cookie, and says what happened: a right guess proves the code and keeps it until it is used, a wrong one is counted on it, five make it dead, and a code past its ten minutes is expired. A null guess only asks whether the code is proven, which is how a person in several families chooses one after the code |
| `key_use` | Uses a proven code, once: deletes it and returns it |
| `login_by_address` | The login for an address, before any family is known, as its id and nothing else |
| `my_families` | The families the signed-in person can choose between |

A children's view is written inside the parent's transaction ([auth.md](auth.md), flow 5): one `kid-session` key per child, each naming the child and the parent who opened it, sharing one view id in `detail`, with the parent's own session key on that browser deleted in the same transaction. Checks on the table refuse a `kid-session` key without a kid and a parent, and a `pin` key that names a kid, and a partial unique index keeps one `pin` key per family, so setting the PIN again replaces the row. A PIN's wrong tries are counted on its row under a lock on that row, so two tries at the same moment are taken in turn.

The rate limits are [auth.md](auth.md)'s and are counted from these rows, so there is no table of counters. For an address: one sign-in or confirm code a minute, three in fifteen minutes and ten a day, and none while its codes have had ten wrong guesses in the last hour. For a network: twenty codes an hour. For everyone: five hundred unused codes and invitations an hour, after which sending stops. A code's wrong guesses and a family PIN's wrong tries are counted on the key itself. None of the numbers is measured.

### The log

`id` is a uuid the writer makes, and it is what makes a replayed upload write nothing twice. `(family_id, device, seq)` stays unique beside it, and the server takes every writer's next number under a lock on the family's row, so no two events share a place in one writer's stream, and a different event claiming a place another already holds is refused rather than dropped, since that is a bug to hear about. `kind` is the only place an event's type lives; `data` is everything else and SQL never reads inside it, so a seventh answer kind is one entry in `engine/answer.ts` and no migration. `at` is when the thing happened, in the one format above, and there is no time the store heard about it: the log reads in the order things happened, then each writer's own order.

`device` is the id of the key the writer signed in with, and has no foreign key, because the log has to keep a stream whose key has ended or been deleted. `actor` is the grown-up who did it, or null when the kid or the system did, and has no foreign key either, because a family's evidence has to outlive a grown-up's login.

A printed sheet is a `sheet-printed` event carrying its questions by value. Paper worked a week after it was printed is three events with three dates (printed, worked, marked), and marking is exact however much the lesson changed in between.

A hash in the log is one of two things, and telling them apart matters. A `pack` digest, and the
`hash` a `content-authored` event carries, name a body somebody saved, so they resolve in the content
table and `GET /api/content/<hash>` answers with the text. A `lessonHash` or an `itemHash` in a
question ref names the level a child was drawn, which is `PackLevel.hash` and `PackItem.hash` in
`engine/pack.ts`: the sha256 of that level's resolved text, worked out by the compiler from the file
the author wrote. A level's text is derived rather than stored, since the catalogue holds what an
author wrote and the levels are made from it, so those two hashes resolve to nothing in the content
table and are not meant to. They are recorded to tell whether the lesson has changed since the
sitting, which is what the product uses them for: a finished day shows no answers and a sitting is
not picked up again when its hash no longer matches (`resumesFor` and `pastSheet` in
apps/kids/lesson.tsx), and a printed sheet is marked at the level it was printed at
(`levelOf` in school/family/sheets.ts and apps/home/mark.tsx). What a child saw is reconstructed from
the lesson's file at that level rather than fetched by the hash (20 September 2026).

### Content

`hash` is generated by Postgres as sha256 of the body, through a small function the migration declares immutable (Postgres marks its own text-to-bytes conversion stable, and converting a given text to UTF-8 always gives the same bytes). `name` and `kind` are written only by `saveContent` in `server/db/content.ts`, from the notation's own declaration line, because working them out in SQL would be a second copy of the notation reader; the guard fails if anything else in the store writes a content row, and a test checks every row of the whole catalogue agrees with its body. The app role may insert and delete a family's rows and may update none, so a revision is immutable. `unique nulls not distinct (family_id, hash)` makes a catalogue revision unique among catalogue rows, which a plain unique would not.

## Isolation

A family's data must never be reachable by another family. Four things hold that, and each is tested.

The app connects as `lumischool_app`, which owns nothing and cannot bypass row-level security. The environment provisions this role before migrations. Locally, `db:up` applies `server/db/migrations/local-roles.sql`; on Neon, provision it once with an environment-specific password using SQL. Migrations grant its privileges and refuse to finish if it can bypass the policies or owns a table. The owner runs migrations and writes the catalogue, and must itself be a superuser or have `BYPASSRLS`, since every table forces row-level security.

Every table has row-level security enabled and forced. Every table with `family_id` has policies that compare it with `app_family()`, a setting read through `nullif`, so a missing setting is null, matches nothing, and returns nothing rather than everything or an error. The catalogue is readable by every family and writable by none. `users` has no family: a login is readable as oneself or through any membership in the current family, and writable only by oneself. `events` is insert and select only for the app role, so "never updated" is a privilege, and `content` has no update at all.

There is one way in: `withFamily({ family, user }, work)` in `server/db/client.ts`. It runs `work` inside one transaction after `set_config('app.family', ..., true)` and the same for `app.user` and `statement_timeout`, so no setting can outlive the transaction on a pooled connection, and the timeout holds through a pooler that does not pass connection settings on. `DB_CONNECT_TIMEOUT` and `DB_STATEMENT_TIMEOUT` set the two waits ([local.md](local.md), "Environment variables"). Inside the transaction, `setScope` moves it to another family or person, for the steps that need it: starting a family, which learns who the person is only once it holds the address's lock; ending the session a person held in one family in the transaction that opens their session in another; and leaving a children's view with the PIN, which learns the parent who opened the view only once it has read the view's keys. Nothing else in the store connects as the app role, the guard fails if any other file opens a connection, and the store's functions take a transaction type that only `withFamily` produces, so passing one an owner connection is a type error.

The policies are generated from `server/db/scope.ts`, which declares for each table the column that names its family and which rows are shared (only the catalogue), and `scope.itest.ts` compares the migrated database policies with the declaration. What a browser receives is the server's to enforce, under [auth.md](auth.md)'s rule: a grown-up's session may receive the whole family, and a children's view only its own children's rows and the kinds of their events auth.md lists, each child's through that child's own key.

The isolation test seeds two families, each with a parent, a kid, a kid-session key, a session, content and a log, plus one person who is a parent in the first and a tutor in the second, and runs everything through `withFamily` with no family filter in any query. With one family set, every select on all seven tables sees none of the other's rows, every update and delete changes none of them, and an insert naming the other family's kid, the other family, or no family at all is refused. With no family set, every table returns nothing but the catalogue. Over ten reuses of one pooled connection, the setting never carried into the next transaction. One family's credential naming another family is refused, and one family's export holds none of the other's ids.

A second test reads the policies back from Postgres, checks that every table is declared in `server/db/scope.ts` or is `users`, and checks that every policy on a family's table compares its family column with the setting, with the catalogue readable by all and writable by none.

## The derived reads

None are stored, and there are no views: sittings, attempts, sheets, the plan and the skill ledger are all folds over `events`. We measured the read the fold needs on the final schema, through `withFamily` and the policies, at [data-model.md](data-model.md)'s upper bound of three children over four years at 1,500 answered events per child-year: 18,000 rows averaging 580 bytes of data, 16 MB of table with its indexes, a median of 34 milliseconds to read one kid's four years and 115 milliseconds for the whole family, on the local container. Row-level security costs nothing measurable at this size. The fold itself is not built and is not in these numbers.

## The guard and the tests

`npm run check:db` enforces eight rules as text, so they hold on a checkout with no database: `engine/answer.ts` imports nothing; `server/db/` reaches only `engine/answer.ts`, node built-ins and its dependencies; nothing outside `server/` imports `server/db/` except the migration config, the guard, and a type-only import of the row types in `server/db/schema.ts`; no app imports anything in `server/` but, as types only, the row types and the API's shapes in `server/api.ts`; every table enables and forces row-level security and has a policy, and every policy on a family table compares `family_id` with the setting, with `users` and `keys` as the only named exceptions; only `server/db/client.ts` opens a connection; only `server/db/content.ts` writes a content row; and the rest of `server/` imports neither the driver nor `drizzle-orm`, so every query is a function in `server/db/`. `--selftest` plants a violation of each and confirms each is reported by the right rule. Relative imports have no extension (CLAUDE.md), and the guard reads one as the `.ts` file `tools/scripts/resolve.ts` finds for Node.

`npm run test:db` checks the schema and replays the real migrations into disposable databases for store, isolation, policy and migration tests. Migration tests also use a non-superuser owner with `BYPASSRLS`, and cover concurrent runs, repeat runs, upgrades with existing rows, corrective SQL and failed-batch recovery. `npm run test:server` creates its own small fixtures through the normal server flows. No test requires an installed demo family. With no database, integration tests skip with a reason; set `LUMISCHOOL_REQUIRE_DB=1` to require them. `npm run check` includes `db:check` for migration metadata.

## What is deliberately not in the database

Anything derived: attempts, sittings, sheets, the plan, the skill ledger, a current lesson per track. All are folds.

Review state. A draft is a revision with no `content-verified` event.

The time the store heard about an event, which nothing reads.

Pack bytes and drawings. A pack's manifest is a content row; the built artefact is a file.

Embeddings. We have nothing to embed, and [ai.md](ai.md) keeps evidence away from a model except through one envelope.

## Redis, and what would make us add it

There is none. We have no cache, no rate limiter that needs one (the limits are counted from `keys`), no fan-out between processes and no background work. The trigger is the first job that has to survive a restart and must not run twice, such as rendering a week of sheets to PDF, and even then a jobs table in this Postgres with `for update skip locked` comes first.

## What auth.md needs the store to confirm

[auth.md](auth.md) is the specification for sign-in, sessions, the children's views and the family PIN, and it lists five things it relies on the store for. All five hold.

1. A `kid-session` key goes with its kid through the `(family_id, kid_id)` foreign key, since a children's view keeps nothing of a child's to erase, and a family has at most one `pin` key.
2. A key's `created_at` can be set on insert, so a session made by switching family keeps the first one's. It is canonical text with a default and a check on its format, and the app role may insert it.
3. A `pin` key's `attempts` and `seen_at` may be written on each try, under a lock on the row. The app role may update and lock keys in its own family.
4. The server's own events take their sequence numbers under a lock on the family's row, and are never written with `on conflict do nothing`. The store's `append` skips only an event whose id is already there, and refuses one that claims a place in a writer's sequence another event holds, so a clash is an error rather than a silent skip; taking the lock is the server's, and the app role may lock its own family's row, since it may update it.
5. The `keys` policy keys every row that has a family on `app.family`, like the other tables, and a key with no family is reachable only through the functions above. The isolation test makes a sign-in code and a confirm code, and shows neither family can see, change, delete or insert one.

Two differences remain, for whoever next edits auth.md. Its link to withdraw consent lasts thirty days, while a `confirm` code lasts ten minutes, so that link needs a kind of its own or a different lifetime. And a few definer functions it lists are not built, because nothing calls them yet: finding a login by id (for passkeys), counting keys for a limit separately from making one (the limits are applied inside `key_issue`), and listing the families a sweep has work in. Finding a login by address is built, as `login_by_address`, now that sign-in calls it.

## The package manifest

The store has its own dependencies (`drizzle-orm`, `postgres`, and `drizzle-kit`, `typescript` and `@types/node` for development), so the repository has a root `package.json` beside the scratchpad's; it is not a workspace.
